# Forge v2 on Codex CLI

> **Status:** Full support
> **Adapter:** `adapters/codex/`
> **Context file:** `AGENTS.md` (repository root)

---

## What is Codex CLI?

Codex CLI is OpenAI's terminal agent. It runs in full-auto mode: it reads the project context from `AGENTS.md` at the repository root, executes shell commands, edits files, and can complete complex development tasks without manual intervention at each step.

Unlike Claude Code (which uses `.claude/` and slash commands), Codex has no registrable command system. The way to give it structured instructions is through prompt templates that the user pastes into the session.

---

## Quick install

```bash
# Initialize forge in the project (generates project.yaml + agents + hooks)
npx @cristiancorreau/forge init

# Generate the native Codex configuration (AGENTS.md + .codex/)
npx @cristiancorreau/forge generate --runtime codex
```

`forge generate --runtime codex` reads `project.yaml` and produces:

- **[OK] AGENTS.md** — generates the context file from `project.yaml`
- **[OK] .codex/** — creates the directory and the configuration (`codex.yaml`, onStart/onFinish hooks)

When done, commit the generated files:

```bash
git add AGENTS.md .codex/
git commit -m 'chore(codex): initialize Forge v2 Codex adapter'
```

## How Forge works in Codex

### AGENTS.md as the agent's memory

Codex CLI loads `AGENTS.md` from the repository root at the start of every session. It is the equivalent of `CLAUDE.md` in Claude Code, but geared toward autonomous execution: it includes security rules and autonomy limits inline because Codex has no hook mechanism that can block individual actions.

Forge generates `AGENTS.md` with the CLI command `npx @cristiancorreau/forge generate --runtime codex`, which reads `project.yaml` and produces:

- **Stack** — language, backend, frontend, database, testing
- **SDD workflow** — spec-before-code rule, implementation steps
- **Security rules** — no hardcoding of secrets, parameterized queries, no force push to main
- **Autonomy limits** — don't delete files without confirmation, run tests before marking complete
- **Agent roster** — the project's active, compliance, and specialized agents (with descriptions read from `core/agents/` or `profiles/`)
- **Forge v2 Commands** — table of available commands with a reference to each template file
- **Production rules (pre-bash-check)** — list of commands blocked in a production context
- **Branch guard** — instruction not to edit code directly on `main` or `master`

To regenerate `AGENTS.md` after changing `project.yaml`:

```bash
npx @cristiancorreau/forge generate --runtime codex
```

### Commands (prompt templates, not slash commands)

Codex CLI does not support slash commands. Forge provides prompt templates in `adapters/codex/commands/` that the user pastes at the start of the session or when they need to perform a specific action.

| Command | File | When to use it |
|---------|---------|---------------|
| `session-start` | `adapters/codex/commands/session-start.md` | At the start of each work session |
| `plan` | `adapters/codex/commands/plan.md` | Before implementing — verifies or creates the spec |
| `work` | `adapters/codex/commands/work.md` | Implement a feature with an APPROVED spec |
| `review` | `adapters/codex/commands/review.md` | Review code or changes before the merge |
| `ship` | `adapters/codex/commands/ship.md` | Verify that the project is ready to deploy |
| `session-close` | `adapters/codex/commands/session-close.md` | At the end of each work session |

**How to use them:** each file has a frontmatter with `name`, `description`, and `usage`, followed by a `## Prompt para Codex` section. Copy the contents of that section, replace the bracketed placeholders (`[NOMBRE O RUTA A LA SPEC]`, etc.), and paste it into the Codex session.

Example with `work.md`:

```
Implementa la siguiente feature: F2-08 — Codex CLI runtime docs

Sigue estos pasos en orden estricto:
1. Verificar spec aprobada
   - Lee docs/specs/F2-08-codex-runtime-docs.md
   ...
```

### Hooks (onStart / onFinish)

Codex CLI supports three hook events configurable in `.codex/codex.yaml`:

| Hook | Claude Code equivalent | When it runs |
|------|---------------------------|--------------|
| `onStart` | `UserPromptSubmit` / `SessionStart` | At the start of each session |
| `onFinish` | `Stop` | At the end of the session |
| `onDiff` | (no direct equivalent) | When Codex applies changes to the filesystem |

Forge configures `onStart` and `onFinish`. The `.codex/codex.yaml` generated by the setup:

```yaml
model: o4-mini  # cambiar según preferencia: o4-mini | o3 | gpt-4o

hooks:
  onStart:  bash .codex/forge-codex-start.sh
  onFinish: bash .codex/forge-codex-finish.sh
```

**forge-codex-start.sh** checks at the start of each session:

1. git and node available in PATH
2. Current branch is not `main` or `master` (warns if it is)
3. Uncommitted changes in the worktree (warn)
4. `project.yaml` exists (warns if not)
5. `project.yaml` has `project.name` and `project.mode` (warns if missing)
6. `PROD_*` / `PRODUCTION_*` environment variables active (warns if any)

If everything is clean, the hook prints nothing. If there are warnings, it lists them with descriptive labels. Unlike Claude Code, **the onStart hook cannot block the session**: it always ends with `exit 0`.

**forge-codex-finish.sh** runs when closing each session:

1. Detects modified or staged files with `git diff`
2. Reads `project.yaml` to find the configured check command (`scripts.check`)
3. If no command is configured, auto-detects by file type:
   - TypeScript/TSX: `tsc --noEmit` (or `pnpm turbo typecheck` in monorepos)
   - Python: `python3 -m py_compile` per file
   - PHP: `composer validate`
   - Ruby: `bundle exec ruby -c`
4. Prints the check result to the terminal
5. Always ends with `exit 0`

## Critical differences vs Claude Code

| Feature | Claude Code | Codex CLI |
|---------|-------------|-----------|
| Context file | `CLAUDE.md` | `AGENTS.md` |
| Commands | Slash commands (`/plan`, `/work`, etc.) | Prompt templates in `adapters/codex/commands/` |
| Pre-action hook | `PreToolUse` (can block) | Not available |
| Post-action hook | `PostToolUse` | Not available |
| Session hook | `UserPromptSubmit` / `Stop` per turn | `onStart` / `onFinish` per session |
| Filesystem hook | Not available | `onDiff` |
| Hook blocking | Yes (`exit 2` stops the session) | No (informational only, always `exit 0`) |
| Parallel agents | Subagents with worktrees + `SendMessage` | Full-auto only |
| Deploy with MCP | Vercel MCP tools | CLI commands (`ship.md` template) |
| Branch guard | `PreToolUse` hook blocks editing on main | Instruction in `AGENTS.md` (voluntary) |
| Debug detection | `Stop` hook reviews files automatically | `forge-codex-finish.sh` on session close |
| Review status | `.claude/review-status.json` | No native equivalent |

## Daily use

Recommended SDD flow for a typical session:

**1. Start the session** — paste the `session-start.md` prompt:

```
Inicia la sesión de trabajo. Ejecuta estos checks en orden y reporta el resultado:
1. Verificar herramientas disponibles...
```

Codex checks the branch, uncommitted changes, and `project.yaml`, then reports:

```
Sesión iniciada — Mi Proyecto
Branch: feature/auth-refresh-2026-05-17
Estado: limpio
Warnings: ninguno
```

**2. Plan** — paste the `plan.md` prompt with the feature name:

```
Quiero planificar la siguiente feature: auth token refresh
```

Codex looks for the spec in `docs/specs/`, creates it if it doesn't exist (`DRAFT` status), or proposes the implementation plan if it is `APPROVED`.

**3. Implement** — paste the `work.md` prompt with the path to the spec:

```
Implementa la siguiente feature: docs/specs/F2-09-auth-token-refresh.md
```

Codex verifies that the spec is in `APPROVED` status, implements in the correct order (schema → types → backend → frontend → tests), and updates the spec to `IMPLEMENTED` when finished.

**4. Review** — paste the `review.md` prompt:

```
Revisa el siguiente código: cambios sin commitear actuales
```

Codex runs the security and quality checklist and reports blockers, warnings, and suggestions.

**5. Prepare deploy** — paste the `ship.md` prompt:

```
Prepara el proyecto para deploy en: staging
```

Codex verifies a clean worktree, runs tests and build, and checks environment variables and debug statements.

**6. Close the session** — paste the `session-close.md` prompt. Codex records what was completed, what is pending, and the final state of the repo.

## Known limitations

- **No slash commands.** There is no registrable command mechanism. Prompt templates are the workaround: they require manual user action (copy and paste).

- **No parallel subagents.** Codex operates in full-auto mode only. Forge's pattern of spawning subagents with worktrees and `SendMessage` is specific to Claude Code and has no equivalent in Codex CLI.

- **onStart cannot block.** Unlike Claude Code's `UserPromptSubmit` hook (which can end with `exit 2` to stop the session), Codex's `onStart` hook always continues regardless of the exit code. Warnings are informational.

- **onFinish runs per session, not per turn.** Claude Code runs the `Stop` hook at the end of each agent turn. Codex runs `onFinish` only once when closing the full session, which reduces the granularity of post-action checks.

- **No PreToolUse / PostToolUse.** Codex cannot intercept individual tools before or after executing them. Security rules (branch guard, pre-bash-check) are embedded in `AGENTS.md` as text instructions. The agent must respect them voluntarily; there is no mechanical enforcement.

- **No review-status.json.** Claude Code maintains `.claude/review-status.json` to track the review status between sessions. Codex has no native equivalent mechanism; tracking must be done in the frontmatter of the specs (`docs/specs/`).

## Security

Codex CLI operates in full-auto mode: it can execute shell commands, edit files, and make commits without confirmation per individual action. In the absence of `PreToolUse` hooks, **`AGENTS.md` is the only active enforcement layer**.

The security rules embedded in `AGENTS.md` cover:

- No hardcoding of tokens, passwords, or secrets
- SQL queries with prepared parameters
- No PII in logs
- Authentication and authorization verification on every endpoint
- No force push to main/master
- Destructive database commands blocked in a production context
- Branch guard: don't edit source code directly on `main` or `master`

**For work that touches production**, use the `--approval-mode suggest` flag:

```bash
codex --approval-mode suggest
```

In this mode, Codex proposes each action and waits for explicit confirmation before executing it. It is the closest equivalent to the mechanical protection provided by Claude Code's `PreToolUse` hook.

If the project is high-risk (production database, user data, payment systems), consider using Claude Code as the primary runtime, which can indeed block destructive commands before executing them.
